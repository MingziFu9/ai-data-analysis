# 附录 E 报告与规范模板

数据工作的成果，一半是数据和代码，一半是文档。本附录收集了书中各章要求撰写的文档模板，按项目的先后顺序排列。每个模板都给出“写什么”和一个简短的示例，示例取自“食客说”案例；方括号 `[ ]` 里的内容按实际情况填写。

**通用要求：**

- **结论先行**：重要的结论放在最前面，读者可能只看第一段；
- **数字说话**：“质量偏低”不如“准确率 85.2%，低于 95% 的验收标准”；
- **写清版本和日期**：规范和报告都会修订，写明版本号、日期和修订人；
- **不放个人信息**：文档中引用的样例要先脱敏（第 12 章）。

| 模板 | 对应章节 | 谁来写 | 交给谁 |
|---|---|---|---|
| E.1 采集方案 | 3.6 | 数据采集人员 | 需求方、数据提供方 |
| E.2 数据质量评估报告 | 4.1、实验 4-1 | 数据处理人员 | 项目负责人、分析人员 |
| E.3 数据清洗规范 | 4.7、实验 4-2 | 数据处理人员 | 执行清洗的同事、后续使用者 |

| E.6 模型测试报告 | 9.4、实验 9-1 | 建模人员 | 项目负责人、运维人员 |
| E.7 数据分析报告 | 8.6、实验 8-3 | 分析人员 | 业务负责人、决策者 |

## E.1 采集方案

动手采集之前写，和需求方、数据提供方对齐（3.6 节）。

| 项目 | 写什么 | 示例 |
|---|---|---|
| 采集目的 | 数据用来做什么 | 为评论情感分析模型准备训练数据，并统计各商家的好评率 |
| 需要哪些数据 | 数据对象和字段 | 评论（评论编号、商家、用户、评分、内容、时间）；商家名录 |
| 数据源和方式 | 文件、数据库、接口还是网页；用什么账号 | 评论：开放平台评论接口；订单：订单库只读账号 |
| 时间范围 | 起止时间；之后是否增量采集 | 2025 年全年；之后每天增量采集一次 |
| 数据量估计 | 条数、文件大小、请求次数 | 约 1.2 万条，每页 100 条，约 120 次请求 |
| 频率与时间 | 请求频率、运行时间 | 每秒不超过 3 次；每日凌晨 2 点运行 |
| 合规与安全 | 授权依据、不采集哪些字段、密钥和数据怎么保管 | 用户只保留编号；密钥放环境变量；数据不拷贝到个人电脑 |
| 质量检查 | 采集完怎么检查 | 条数与接口 total 一致；编号无重复；每次运行写采集日志 |
| 负责人与交付 | 谁负责，什么时候交付什么 | 小周负责，3 个工作日内交付数据和采集日志 |

## E.2 数据质量评估报告

拿到数据后、清洗之前写，篇幅一页左右（4.1 节）。

```text
《[数据名称]数据质量评估报告》  版本 [v1.0]  日期 [ ]  评估人 [ ]

一、结论（3～5 句）
    [例：订单原始数据共 8120 行，主要问题是下单时间格式不统一（8.58%）、城区写法不标准（7.82%）、
     配送距离缺失或不是数字（共 8.36%）和完全重复的行（1.48%）。处理后可以用于经营分析；
     送达时长有 22 行为负数、29 行超过 180 分钟，分析送达时效前必须先处理。]

二、数据概况
    来源 [ ]   时间范围 [ ]   行数 / 列数 [ ]   主键 [ ]

三、各维度检查结果
    | 维度 | 检查项 | 问题数 | 比例 | 示例 |
    | 完整性 | [配送距离为空] | | | |
    | 唯一性 | [订单编号重复] | | | |
    | 有效性 | [送达时长为负] | | | |
    | 一致性 | [城区写法不统一] | | | |
    | 准确性 | [实付金额 ≠ 订单金额 − 优惠金额] | | | |
    | 及时性 | [下单时间不在统计期内] | | | |

四、对分析的影响
    [哪些问题会影响哪些分析结论，影响有多大]

五、处理建议
    [逐项写：删除 / 填充 / 修正 / 保留并标记 / 退回数据提供方核实]
```

## E.3 数据清洗规范

写给“照着就能做”的同事，每一条都要具体到可以直接执行（4.7 节）。

```text
《[数据名称]清洗规范》  版本 [v1.0]  日期 [ ]  编写人 [ ]  适用数据 [ ]

一、处理顺序
    格式统一 → 去重 → 异常值 → 缺失值 → 派生字段（顺序不同，结果可能不同）

二、清洗规则
    | 序号 | 字段 | 问题 | 判断方法 | 处理方式 | 理由 |
    | 1 | 订单编号 | 完全重复的行 | duplicated() | 保留第一条 | 系统重复上报 |
    | 2 | 城区 | “天河区”“Tianhe” | 对照表 | 统一为“天河” | 便于分组 |
    | 3 | 送达时长 | 小于 0 | 业务规则 | 置为缺失 | 系统时钟错误 |
    | 4 | 配送距离 | 为空 | isna() | 按城区中位数填充，加标记列 | 同城区距离相近 |
    | [ ] | | | | | |

三、清洗后检查
    行数变化 [8120 → ]；每条规则处理了多少行；关键统计量清洗前后对比

四、数据字典（清洗后）
    | 字段 | 含义 | 类型 | 单位 | 取值范围 | 备注 |
    | 配送距离 | 商家到收货地址的距离 | 小数 | 千米 | 0～15 | 部分为填充值，见“距离为填充值”列 |

五、修订记录
    | 版本 | 日期 | 修订内容 | 修订人 |
```

## E.4 标注规范

标注规范决定了数据的质量，要经过试标、讨论、修订才能定稿。完整的示例见 `labs/ch05/标注规范_v1.0.md`（5.4 节）。

```text
《[任务名称]标注规范》  版本 [v1.0]  日期 [ ]

1. 任务说明
    目的 [训练什么模型 / 统计什么]   对象 [什么数据，是否已脱敏]
    每条数据标几项 [ ]   工具 [Label Studio，模板文件]

2. 标签定义（每个标签：定义 + 正例 + 反例）
    | 标签 | 定义 | 正例 | 反例（不属于本类） |

3. 边界规则（拿不准时怎么办，按出现频率排序）
    1) [好坏都有时，看结尾和整体态度……]
    2) [ ]

4. 操作要求
    [实体只划名称本身，不含修饰词；无法判断的点“跳过”并备注原因；每天提交前自查]

5. 质量要求
    [抽检准确率 ≥ 95% 为合格；不合格整批返工]

6. 疑难样例（试标中发现的，附正确答案和理由）

7. 修订记录
    | 版本 | 日期 | 修订内容（新增 / 修改了哪条规则） | 依据（试标中发现的问题） |
```

## E.5 标注审核报告

质检和验收后写，结论要有数字支撑（6.3 节）。

| 部分 | 写什么 | 示例（实验 6-2） |
|---|---|---|
| 基本情况 | 批次、数据量、标注员、标注时间、规范版本 | 第 1 批，2000 条，W01～W04，规范 v1.0 |
| 抽检方案 | 抽样方法、比例、合格标准、加抽规则 | 按标注员分层抽 10%，准确率 ≥ 95% 合格，不合格加抽 20% |
| 抽检结果 | 整批和每人的抽检条数、准确率、结论 | 整批 93.0%；W03 加抽后 85.2%，其余合格 |
| 错误分析 | 错误类型分布、典型错误样例、原因 | 正面误标为中性最多，标注员对“中性”理解过宽 |
| 处理意见 | 返工范围、规范修订、培训建议 | W03 的 409 条返工；规范补充中性的反例 |
| 附件 | 抽检明细、返工清单 | `返工清单.csv` |

## E.6 模型测试报告

模型交付使用前写，说清楚“在什么数据上、有多好、哪里不好”（9.4 节）。

```text
《[模型名称]测试报告》  模型版本 [ ]  日期 [ ]  测试人 [ ]

一、结论
    [例：情感分类模型在 2000 条测试评论上准确率 96.3%；负面、中性召回率较高，
     正面误判为中性的较多。建议上线，并对“好坏各半”的评论人工复核。]

二、数据
    训练数据 [来源、条数、标签分布、标注规范版本]
    测试数据 [来源、条数；与训练数据是否有重叠]

三、方法
    特征 [ ]   模型 [ ]   主要参数 [ ]   对比的基线 [如“全部猜最多的类”]

四、结果
    总体指标 [准确率 / MAE / R² 等，与基线对比]
    分类别指标 [每类的精确率、召回率]   混淆矩阵 [图或表]

五、错误分析
    [错误条数；按类型归类；典型错误样例 5～10 条；可能的原因]

六、使用建议与局限
    [适用范围；不适用的情况；需要人工复核的情况；何时需要重新训练]
```

## E.7 数据分析报告

写给决策者看，最重要的是“结论先行、一条发现配一张图、建议可执行”（8.6 节）。

```text
《[报告标题，最好直接写出主要结论]》  日期 [ ]  作者 [ ]

摘要（半页以内，3～5 句：最重要的发现和建议）

一、背景与问题
    [为什么做这次分析；要回答哪几个问题]

二、数据与方法
    [数据来源、时间范围、条数；做了哪些清洗；用了哪些方法（描述统计、检验、建模……）]

三、分析发现（每条：一句结论 + 一张图 + 支撑的数字）
    发现 1：[例：送达超过 40 分钟的订单好评率低 9 个百分点]
        [图]  [数字：超过 40 分钟的订单占 7.7%，好评率 55.0%，其他订单 63.9%，卡方检验 p < 0.001]
    发现 2：[ ]
    ……

四、建议
    | 建议 | 依据（对应发现） | 谁来做 | 预期效果 | 怎么验证 |

五、局限与下一步
    [数据和方法的不足；相关不等于因果；还需要什么数据或实验来验证]

附录：数据字典、详细表格、代码位置
```

## E.9 优化需求

发现的问题要变成别人能直接执行的需求，一个问题写一份（11.6 节）。

| 项目 | 写什么 | 示例 |
|---|---|---|
| 需求标题 | 一句话说清要做什么 | 情感模型补充“新说法”评论的训练数据 |
| 提出人 / 日期 | | 运维小李，[日期] |
| 问题描述 | 现象和影响范围，配数据 | 第 5 周起约 30% 的评论出现“绝绝子”“yyds”“是预制菜吧”等新说法，这部分评论抽检准确率 93.5%，比其他评论（96.4%）低约 3 个百分点 |
| 原因分析 | 归因结论和依据 | 训练数据中没有这些说法，属于数据漂移；“是预制菜吧”的归类在标注规范中没有规定 |
| 建议方案 | 怎么改 | 补标 1000 条含新说法的评论后重新训练；标注规范增加相应边界规则 |
| 验收标准 | 怎样算完成 | 新说法评论的抽检准确率不低于 96%（实验 11-3 补标 1000 条后达到 97.0%） |
| 优先级 / 期望完成时间 | 高、中、低 | 高，两周内 |
| 负责团队 | | 数据标注组、算法组 |

## E.11 综合项目报告

第 12 章综合项目提交的报告，结构参照数据分析报告，增加“数据处理过程”和“合规检查”两部分，正文 8～15 页（12.6 节）。

```text
《[项目题目]》  小组成员及分工 [ ]  日期 [ ]

摘要（半页：问题、主要发现、建议）

一、项目背景与问题
二、数据处理过程
    2.1 数据来源与采集（附采集方案）
    2.2 数据质量评估（附评估报告）
    2.3 清洗与脱敏（附清洗规范；清洗前后的行数和问题数）
三、标注（如有）
    标注规范要点、试标与修订、一致性或抽检结果
四、分析与建模
    方法、结果（附测试报告或统计检验结果）
五、发现与建议（每条发现配图和数字）
六、合规检查（附合规检查表；说明数据可能存在的偏差）
七、局限与下一步
附录：代码清单、看板截图、组员贡献说明
```

答辩用 PPT 控制在 10 页左右、讲 10 分钟：问题 1 页、数据和处理 2 页、发现 3～4 页、建议 1 页、合规 1 页、总结 1 页。
